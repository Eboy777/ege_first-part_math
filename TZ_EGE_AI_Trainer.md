# Техническое задание: тренажёр первой части профильного ЕГЭ по математике

**Статус:** функциональное ТЗ для согласования перед разработкой.  
**Охват:** логика продукта, страницы, элементы интерфейса, поведение, данные, проверки и этапы реализации.  
**Не входит в это ТЗ:** цветовая палитра, шрифты, анимации, иллюстрации, окончательная визуальная композиция.

## 1. Цель и границы продукта

Создать веб-тренажёр, в котором школьник:

1. Входит по выданному администратором логину и паролю.
2. На главной странице выбирает номер первой части профильного ЕГЭ, затем тип задачи.
3. Изучает теорию и пример решения выбранного типа.
4. Выполняет **5 задач последовательно**: первые 3 — обучающие (подсказки разрешены), следующие 2 — контрольные (для зачёта без помощи ИИ).
5. Через 7, 30 и 90 дней после освоения типа проходит повторения, каждое из **2 контрольных задач**.
6. В любой момент открывает бокового ИИ-помощника; если нет активной задачи платформы, может присылать в чат собственные задачи, в том числе фотографии.
7. При неверном ответе на задачу платформы попадает в диалог разбора; ошибка записывается в отдельный файл ученика **только после его объяснения хода решения и определения причины**.
8. Через отдельную кнопку на главной странице входит в режим «Отработка ошибок», где ИИ предлагает на выбор 5 наименее отработанных ошибок и выдаёт задачу по выбранной.

**Не разрабатывать на данном этапе:** ачивки, рейтинги, соревнования, Telegram-бота, регистрацию для учеников, платёжную систему, кабинет учителя, полнофункциональную административную панель, прогноз баллов ЕГЭ.

**Версия экзамена:** каталог обязан поддерживать `exam_version`, потому что нумерация меняется. В ЕГЭ-2026 первая часть содержит 12 задач; в опубликованном проекте ЕГЭ-2027 — 13. До наполнения каталога согласовать целевой год и проверить актуальную спецификацию ФИПИ. Не зашивать номера, названия и типы задач в компоненты интерфейса. **Важно:** методички текущего EduAI привязаны к старой нумерации, поэтому при выборе ЕГЭ-2027 нужно проверить и переназначить связь «номер → тип → методичка», а не просто менять заголовки.

## 2. Карта страниц и расположение функций

### 2.1. Страница авторизации `/login`

- Поля «Логин» и «Пароль», действие «Войти», сообщение об ошибке при неверных данных.
- Саморегистрации и восстановления по почте нет.
- После входа — главная страница; после выхода — возврат на `/login`.
- Все остальные страницы доступны только после авторизации.

### 2.2. Главная страница `/`

Содержит:

- Название тренажёра и текущую версию экзамена.
- **Карту первой части**: группы «Геометрия», «Вероятность и статистика», «Алгебра», «Функции и анализ», «Практические задачи» (точный состав формируется каталогом).
- В каждой группе — карточки номеров ЕГЭ: номер, название, число освоенных типов / всех типов, индикатор прогресса; при необходимости — иконку повторения с **числом типов**, ожидающих повторения.
- Отдельную заметную кнопку **«Отработка ошибок»**.
- Постоянную кнопку открытия **бокового ИИ-чата**.
- Действие выхода из аккаунта.

Нажатие на номер открывает страницу соответствующего номера. Клик по индикатору повторений ведёт к его типам, которым требуется повторение.

### 2.3. Страница номера `/exam/:examVersion/tasks/:number`

- Название и номер ЕГЭ, навигация назад на карту.
- Список **типов задач** этого номера.
- Каждый тип представлен отдельным кликабельным компактным блоком: название, «N/5», **пятисегментная шкала** (первые 3 сегмента — обучение, последние 2 — контроль), при необходимости иконка «Нужно повторить» и статус повторений.
- До решения все сегменты пустые. По успешному завершению задач заполняются по одному. Значения хранятся отдельно от визуальных цветов, которые определяются при дизайн-этапе.
- Нажатие на тип открывает его страницу.
- Список доступен целиком, без блокировки других типов.
- Кнопка бокового ИИ-чата доступна здесь тоже.

### 2.4. Страница типа `/exam/:examVersion/types/:typeId`

**До старта тренировки:**

- Название номера и типа.
- Прогресс `N/5`, компактная пятисегментная шкала.
- Блок теории и **один разобранный пример** именно этого типа.
- Кнопка «Тренироваться» или «Продолжить».
- При уже освоенном типе — статус и возможность начать назначенное повторение, если оно наступило.

**После нажатия «Тренироваться»:**

- Блок теории автоматически сворачивается, но остаётся доступен для раскрытия.
- Показывается **только одна активная задача**: условие, необходимые математические изображения/чертежи, поле ответа, кнопка «Ответить».
- На этапах 1–3 **рядом с «Ответить» есть «Получить подсказку»**: кнопка открывает панель ИИ и передаёт запрос о текущей задаче.
- На этапах 4–5 кнопки подсказки нет.
- Следующая задача **не доступна**, пока текущая корректно не завершена по правилам своего этапа; уход со страницы или перезагрузка не теряет прогресс.
- После корректного выполнения этапа — обратная связь и действие «Следующая задача», при последнем этапе — «Тип освоен».
- Боковой чат всегда доступен, включая контрольный этап, но обращение за содержательной помощью по контрольной задаче аннулирует самостоятельность **этой попытки**; для зачёта потребуется новая задача.

### 2.5. Боковая панель ИИ (общий компонент сайта)

- Постоянная кнопка открытия/закрытия в доступной области интерфейса.
- Панель появляется сбоку от основного содержимого, не заменяя страницу. На узком экране — отдельная выдвижная область с возможностью закрыть.
- Лента сообщений (один основной чат ученика), поле ввода, отправка сообщения, прикрепление фотографии, просмотр прикреплённого изображения.
- При открытой задаче ИИ получает её **идентификатор, условие, тип, текущий этап и режим**.
- При отсутствии активной задачи передаётся `active_task_id: null`, и ученик может свободно присылать собственные задачи текстом/фотографиями. Такие задачи **не изменяют пятиступенчатый прогресс** и **не пополняют файл ошибок**, поскольку не являются проверяемыми задачами платформы.
- Основной чат не очищается при переходах между страницами или задачами. Отображается сохранённая переписка; в запрос модели автоматически передаются **только 10 последних сообщений** данного диалога, плюс инструкции и текущий контекст.
- Для старого сообщения можно выделить текст и нажать «Спросить ИИ»: выбранный фрагмент явным образом добавляется в новый запрос независимо от того, когда он был написан. Не подмешивать остальные старые сообщения автоматически.
- При загрузке фото ИИ сначала извлекает условие и просит подтвердить, что прочитал верно, затем помогает по алгоритму EduAI.
- Отдельные фото или текстовые сообщения чата не принимаются за ответы на поле задания платформы без явного действия ученика.

### 2.6. Страница «Отработка ошибок» `/mistakes`

- Открывается **только через отдельную кнопку на главной**, но может быть доступна по прямой ссылке после авторизации.
- Представляет собой **отдельный диалог ИИ**, не смешанный с историей основного бокового чата.
- При входе и **после каждого завершённого упражнения** ИИ показывает до **5 ошибок на выбор**, отсортированных по `tasks_solved` по возрастанию; при равенстве — по дате выявления от более ранней к новой.
- Если ошибок меньше пяти, показываются все; если ошибок нет — понятное пустое состояние и переход к обычным заданиям.
- У каждой ошибки показываются короткое описание и число решённых задач в отработке.
- После выбора ошибки ИИ предлагает одну подходящую задачу и ведёт ученика пошагово по существующим правилам EduAI.
- После успешного решения **одной уникальной задачи** счётчик `tasks_solved` выбранной ошибки увеличивается на 1, затем список из пяти пересчитывается и предлагается заново.
- При неверном решении счётчик не растёт; ИИ помогает завершить эту задачу. Нельзя получить несколько зачётов многократной отправкой одного правильного ответа.
- Файл ошибок ученика разрешено читать и использовать для персонализации **только здесь**. В основном чате и обычном обучении он не передаётся ИИ.
- Долговременная память этой отдельной беседы — только файл ошибок; модель получает последние 10 сообщений беседы и текущую выбранную ошибку/задачу.

## 3. Логика пятиступенчатого обучения

### 3.1. Начало

- Все ученики обязательно выполняют все 5 этапов, ускоренного пропуска нет.
- Этапы 1, 2, 3 — обучающие. Подсказка разрешена, но необязательна.
- Этапы 4, 5 — контрольные. Засчитываются только при решении **без подсказок к данной попытке**.
- Задачи для последовательных этапов отличаются (не повторять то же условие при новой контрольной попытке).
- Первую задачу типа создаёт/выдаёт банк проверенных задач. После завершения текущей система выбирает следующую задачу того же типа.

### 3.2. Проверка ответа

- У задачи есть сохранённый проверяемый правильный ответ и правило нормализации ответа (например, запятая/точка, знак, пробелы, допустимые форматы чисел). Результат «верно/неверно» определяется проверяющим модулем, **а не свободным выводом ИИ**.
- При пустом или некорректно отформатированном вводе показать ошибку ввода; **не считать это математической ошибкой** и не открывать диагностический ИИ-разбор.
- Если ответ правильный:
  - обучающий этап — заполнить следующий сегмент независимо от того, были подсказки или нет;
  - контрольный этап — заполнить сегмент **только при независимой попытке**;
  - показать подтверждение и разрешить перейти к следующей задаче.
- Если ответ неправильный: открыть боковую панель ИИ с текущей задачей и предложением **«Объясни, как ты решал»**. Этап не засчитывается.
- При неправильном ответе на контрольном этапе или запросе подсказки по нему отметить текущую попытку `assisted=true` / `independent=false`. После разбора/исправления ученик получает **новую контрольную задачу** того же этапа. Текущая задача не может принести контрольный сегмент.
- При неправильном ответе на обучающем этапе ученик вместе с ИИ находит ошибку, исправляет решение, подаёт верный ответ в проверку и только после этого открывает следующий этап.
- Перезагрузка страницы, уход в другую часть карты и закрытие панели не должны менять статус попытки и не должны открывать следующую задачу раньше времени.

### 3.3. Состояния, которые нужно различать

- `stage_index`: 1–5.
- `attempt_status`: active / incorrect / solved / replaced.
- `assisted`: обращение за помощью по текущей задаче в контроле.
- `stage_completed_at`: фиксация успешного зачёта каждого этапа.
- `type_mastered_at`: дата правильного завершения всех пяти этапов.

Клиент не может сам отметить этап пройденным: сервер валидирует этап, задачу, правильность, самостоятельность и отсутствие повторного зачёта.

## 4. Система повторений

- После завершения 5/5 создаётся расписание трёх проверок: **через 7, 30 и 90 дней от `type_mastered_at`**.
- Каждая проверка состоит из **2 новых контрольных задач** по тому же типу; обе должны быть решены самостоятельно.
- Задачи повторения проходят последовательно. Если контрольная попытка не засчитана, ИИ помогает разобраться, затем выдаётся новая контрольная задача того же шага.
- Если ученик не закончил повторение, оно остаётся в статусе `due/in_progress`; базовый прогресс **5/5 не обнуляется**.
- После прохождения 2/2 соответствующая проверка отмечается выполненной. Следующие запланированные даты относительно первоначального освоения не сдвигаются.
- Если ученик пропустил несколько дат, показывать **одно актуальное требование повторения на тип**, а не несколько одинаковых уведомлений. При закрытии проверки система переходит к следующей уже наступившей контрольной точке, не выдумывая прохождение пропущенных.
- На типе — маркер «Пора повторить» и прогресс текущего повторения `0/2` или `1/2`; на карточке номера — **число разных типов** с наступившим и ещё не завершённым повторением. Группа/карта также могут агрегировать это число.
- Повторение не создаёт новых сегментов основного прогресса и не влияет на `tasks_solved` файла ошибок.

## 5. Диагностика и файл ошибок

### 5.1. Строгое условие записи

Запись ошибки разрешается только в цепочке:

1. Ученик отправил **неверный ответ в поле проверяемой задачи платформы**.
2. Система открыла ИИ-разбор и спросила, как он решал.
3. Ученик **описал ход решения** (если недостаточно информации — ИИ уточняет).
4. ИИ выявил конкретную причину ошибки; если причины достоверно нет — не записывать.
5. Система проверила, что такой `error_key` ещё не существует в файле этого ученика. Если существует — не создавать дубль.

**Недостаточно для записи:** одна неправильная цифра без объяснения ученика; теория, просмотренная в интерфейсе; гипотеза ИИ без ответа ученика; свободный чат со своей задачей.

### 5.2. Структура файла

По одному защищённому структурированному файлу на ученика, например `private/student_errors/<internal_user_id>.json` (не в публичной папке и не в git). Не использовать логин в имени файла. Пример:

```json
{
  "user_id": "internal-id",
  "errors": [
    {
      "error_key": "quadratic:discriminant_sign",
      "title": "Ошибка со знаком дискриминанта",
      "description": "При вычислении D ошибается со знаками",
      "related_type_ids": ["quadratic_equations"],
      "tasks_solved": 2,
      "first_detected_at": "2026-10-30T18:00:00Z"
    }
  ]
}
```

- Для исключения дублей использовать **устойчивый ключ ошибки**, а не буквальное совпадение фразы ИИ. Нужен справочник кодов распространённых ошибок; для новой неизвестной ошибки — осторожная классификация, при неоднозначности без записи.
- Файл должен безопасно обновляться при одновременных запросах (блокировка/атомарная запись или транзакционная реализация).
- Счётчик `tasks_solved` меняется **только после успешно выполненной задачи режима «Отработка ошибок»**. Он не равен количеству обычных задач или обнаружений ошибки.
- Ошибки не удаляются автоматически и не передаются в обычную учебную беседу.

### 5.3. Режим отработки

Список из 5 — **выбор пользователем**, а не принудительный автоматический переход на первую ошибку. После любого успешно завершённого задания сортировка выполняется заново. Каждая задача имеет явную привязку к выбранному `error_key`, чтобы правильно обновить счётчик.

## 6. Логика ИИ и контекста

### 6.1. Основной ИИ-наставник

- Использовать педагогические правила EduAI: один содержательный шаг за сообщение, наводящие вопросы, не выдавать полное решение раньше времени, учитывать текущую задачу.
- Подключать методику по типу задачи через RAG/явную привязку к методичке. Подключение методики не должно зависеть только от похожести произвольного текста. Проверить состав и актуальность базы RAG: в репозитории скрипт индексации читает `bot/methods_v3`, а там пока обнаружен только материал `task_1.txt`; полный набор методичек расположен в `bot/methods_v2`.
- Основная беседа **одна на пользователя**, даже при переключении разделов; видимая история может храниться для отображения и выбора цитат. Модель получает только **последние 10 сообщений**, а не весь архив.
- К каждому запросу добавлять актуальный технический контекст: `user_id`, `mode=regular|free_chat`, `active_task_id` (или `null`), `type_id`, `exam_version`, `stage_index`, `task_statement`, `assistance_allowed`.
- При переключении страницы контекст задачи меняется немедленно. ИИ не должен продолжать решать старую задачу как текущую.
- При отсутствии активной задачи ИИ может разбирать задачи ученика, отправленные текстом или фото, без связи с прогрессом платформы.
- Файл ошибок ученика не читать в обычном чате.

### 6.2. Контроль самостоятельности

- Помощь по активной контрольной задаче запрещает зачёт **данной попытки** как самостоятельной.
- При любом запросе к ИИ, который раскрывает путь решения текущего контроля, сервер отмечает попытку как `assisted` **до отправки ответа ИИ**. ИИ может помочь разобраться, но для зелёного пункта нужна другая задача.
- Допустимы технические вопросы об интерфейсе без сброса самостоятельности, но для первого релиза безопаснее явно различать два действия: помощь по текущей задаче и общие вопросы.

### 6.3. Два диалога

- `main_conversation`: единственный боковой чат ученика для обычных задач и свободных задач с фото.
- `mistakes_conversation`: отдельная беседа только на странице `/mistakes`, доступная вместе с файлом ошибок.
- У каждой беседы свой поток сообщений и окно последних 10 сообщений. Смешивать их нельзя.
- Для цитирования старого текста пользователь выделяет фрагмент и нажимает «Спросить ИИ»: передать только явно выбранный текст вместе с новым сообщением.
- История переписки, которая хранится ради отображения, **не является долгосрочной памятью/профилем ИИ**. В обычном режиме запрещено автоматически создавать постоянные саммари или личные досье.

## 7. Каталог и банк заданий

- Иерархия: `exam_version → section → exam_number → task_type → task`.
- Каждый тип содержит название, теорию, разобранный пример, список проверенных задач, ключи правильных ответов, правила сравнения и связь с методичкой EduAI.
- У каждого задания: стабильный ID, условие, изображения при наличии, правильный ответ в структурном виде, допустимые форматы, решение (не показывается ученику автоматически), метки сложности/типа, статус проверки автором.
- Для каждого типа запас минимум **5 уникальных основных задач + 6 задач повторения + запас для замен при ошибках**. Банк расширяемый; нельзя повторять ту же задачу при замене контрольной попытки.
- Не использовать непроверенные AI-сгенерированные примеры как единственный источник проверочных ответов. Генерация допустима только после проверки задачи и ответа.
- Источники задач должны иметь допустимые условия использования. Содержание и актуальная нумерация согласовываются отдельно; схема не зависит от количества номеров.
- Если в банке закончились подходящие задачи, показать честное сообщение и не выдавать неподтверждённый прогресс.

## 8. Учетные записи, хранение и доступ

- Администратор **вручную создаёт пользователей** (логин + начальный пароль) с помощью защищённого серверного скрипта/команды. Интерфейс регистрации не нужен.
- Администратор может вручную сбросить пароль и заблокировать аккаунт.
- Пароли хранить только как криптографические хеши, не в открытом виде. Сессия должна быть безопасной, с выходом и ограничением попыток входа.
- У каждого ученика отдельно хранятся: аккаунт, прогресс по типам, состояние активной задачи, история проверенных ответов, расписание повторений, сообщения двух чатов для отображения, приватный файл ошибок и ссылки на загруженные фотографии.
- Все пользовательские запросы проверяются по сессии; невозможно прочитать или изменить прогресс/ошибки другого ученика подменой ID.
- Загрузка изображений — с ограничением форматов/размера, без публичного доступа к чужим файлам; ключи AI API только на сервере.
- Состояния и файлы переживают рестарт сервера; нужна резервная копия данных.
- Отдельное API/серверное действие отвечает за выдачу задачи, проверку ответа, зачёт этапа, запуск повторения, регистрацию диагностированной ошибки и увеличение счётчика отработки. Не доверять бизнес-логике браузера.

## 9. Ключевые сценарии и критерии приёмки

| № | Сценарий | Ожидаемый результат |
|---|---|---|
| 1 | Вход по выданному логину/паролю | Открывается личная карта, данные чужих пользователей недоступны |
| 2 | Нажатие номера | Появляются типы этого номера с компактными шкалами |
| 3 | Первый вход в тип | Сначала видны теория и пример; после «Тренироваться» теория сворачивается и появляется одна задача |
| 4 | Решены 3 обучающие задачи | Заполнены три обучающих сегмента, подсказки разрешены |
| 5 | Верный ответ на контрольную без помощи | Зачтён один контрольный сегмент |
| 6 | Неверный ответ в обычной задаче | Открыт основной ИИ; он спрашивает ход решения; следующий этап недоступен |
| 7 | Ученик не объяснил ход решения | Новая ошибка **не записана** |
| 8 | Ученик объяснил, ИИ определил причину | Новая ошибка записана один раз; повторная такая же не дублируется |
| 9 | ИИ помог с контрольной задачей | Попытка не засчитана в контроль; после разбора выдаётся **новая** задача |
| 10 | Решены все 5 задач | Тип 5/5, назначены повторения через 7, 30 и 90 дней |
| 11 | Наступила дата повторения | Маркер на типе и счётчик типов на карточке номера |
| 12 | Решены 2 контрольные задачи повторения | Повторение закрыто; 5/5 остаётся; следующий срок сохраняется |
| 13 | Боковой чат открыт без активной задачи | Можно отправить свою задачу и фото; карта не меняется |
| 14 | Ученик переключился на другую задачу | При запросе к ИИ отправляется ID и контекст **новой** задачи |
| 15 | Выделен фрагмент старого сообщения | В запрос передан выделенный фрагмент + последние 10 сообщений, не вся история |
| 16 | Открыта отработка ошибок | Видны 5 ошибок с наименьшим `tasks_solved`, не главный чат |
| 17 | Решена задача на выбранную ошибку | Счётчик увеличен на 1, список пяти пересортирован |
| 18 | Обновление страницы, выход, повторный вход | Текущая задача, прогресс, расписание и истории доступны, двойного начисления нет |
| 19 | Задачи двух разных учеников | Нет доступа друг к другу по API, файлам и истории диалогов |
| 20 | AI API временно недоступен | Сайт не теряет прогресс; проверка готовых ответов продолжает работать, ИИ сообщает о временной недоступности |

## 10. Рекомендуемые контрольные этапы разработки с AI-агентом

Разрабатывать **поэтапно с явной приёмкой**, а не одним огромным запросом. Оптимально **7 контрольных этапов**. Каждый заканчивается демонстрацией, списком изменений и проверкой, после чего заказчик разрешает переход.

### Этап 1. Уточнение функционала и разработка дизайн-концепции

**Задача агенту:** прочитать это ТЗ, выделить только открытые вопросы, проверить пользовательские пути, согласовать версию ЕГЭ, составить карту экранов и интерактивный прототип без реального бэкенда. Предложить 1–2 визуальных направления отдельно от функционального ТЗ (визуальное решение принимается заказчиком позже).

**Результат:** утверждённые пользовательские сценарии, структура экранов, состояния (обычная тренировка/контроль/повторение/ошибка/свободный чат), прототип для ПК и телефона, список неизменяемых правил.

**Контроль:** заказчик самостоятельно проходит кликами путь «вход → карта → номер → тип → теория → 5 задач → повторение», открывает чат и режим ошибок. **Не переходить к программированию продукта без согласования.**

### Этап 2. Каркас, пользователи, каталог, навигация

**Задача агенту:** реализовать архитектуру, БД, ручное создание пользователей, защищённую авторизацию, страницы и каталог номера/типа из данных; сделать учебную карточку теории и компактную шкалу с демонстрационным прогрессом.

**Результат:** работает вход несколькими пользователями, карта и переходы, аккуратная основа адаптивного интерфейса, тестовый каталог с минимум двумя типами.

**Контроль:** пользователь А не видит данные пользователя Б; любые страницы защищены; навигация и панели работают на мобильном устройстве.

### Этап 3. Движок заданий и прогресс 3+2

**Задача агенту:** реализовать выдачу задач из проверенного банка, проверку ответа, последовательную блокировку, учебные и контрольные попытки, сохранение состояния и заполнение 5 сегментов.

**Результат:** полный цикл 5 задач **без AI** на нескольких типах, включая незачёт контрольной попытки, если она помечена как assisted.

**Контроль:** вручную пройти правильные и неправильные ответы, перезагрузить страницу между этапами, убедиться в невозможности накрутки прогресса.

### Этап 4. Основной ИИ, фотографии и разбор ошибок

**Задача агенту:** интегрировать текущие педагогические правила EduAI, методички/RAG, боковой чат, контекст активной задачи, фотографии, лимит 10 сообщений, выделение старого текста; автоматический разбор неправильного ответа и защищённый файл ошибок.

**Результат:** один постоянный основной чат, свободное решение своих задач при `active_task_id=null`, диагностика только после объяснения ученика, корректная инвалидизация контрольной попытки при помощи ИИ.

**Контроль:** проверить фото и подтверждение распознавания, переключение между задачами, отсутствие ложных записей ошибок, дубликаты, правильный переход к новой контрольной задаче.

### Этап 5. Повторения 7/30/90 и индикаторы

**Задача агенту:** реализовать расписание, очередь наступивших проверок, по 2 контрольные задачи, маркеры повторения на типах и счётчики **числа типов** на номерах.

**Результат:** тип после 5/5 получает три контрольные точки; просроченные проверки не исчезают; 5 сегментов не сбрасываются.

**Контроль:** тестировать с управляемой фиктивной датой сервера/тестовыми данными, чтобы не ждать 7/30/90 дней; проверить несколько просрочек и повторный вход.

### Этап 6. Отдельный режим отработки ошибок

**Задача агенту:** создать страницу `/mistakes`, отдельную историю диалога, сортировку по `tasks_solved`, выбор пяти, выдачу упражнения по выбранной ошибке, инкремент строго после успешного решения и повторную сортировку.

**Результат:** завершённый сценарий «выбрал ошибку → решил задачу → счётчик +1 → новые пять ошибок». Основной чат и файл ошибок в обычной практике не смешиваются.

**Контроль:** 0, 1, 5 и более 5 ошибок; равные значения счётчиков; повторная отправка ответа; перезапуск приложения; ошибки другого аккаунта не видны.

### Этап 7. Полное наполнение, тестирование, публикация

**Задача агенту:** проверить/загрузить каталог и задачи по утверждённой версии экзамена, протестировать всю логику, выполнить адаптивную проверку, устранить проблемы, развернуть серверную и клиентскую части, подготовить инструкцию администратору.

**Результат:** публичный URL с защищённым входом, исходники, команды установки/запуска, инструкция по созданию пользователя и сбросу пароля, тестовые аккаунты для демонстрации, отчёт о проверках и известных ограничениях.

**Контроль:** заказчик лично проходит два полных типа, ошибочную контрольную попытку, свободный чат с фото, отработку ошибки и имитацию повторения на ПК и телефоне. Критические дефекты исправлены до сдачи.

## 11. Как правильно работать с AI-агентом

### Стартовое сообщение агенту

> Ты разрабатываешь веб-тренажёр по приложенному ТЗ. Сначала прочитай ТЗ и существующий EduAI. **Ничего не программируй до согласования этапа 1.** Не меняй правила учебного прогресса, памяти ИИ, ошибок и повторений по собственному усмотрению. Если видишь противоречие, запиши его как вопрос, предложи вариант и дождись решения. Выполняй только текущий этап. После каждого этапа дай ссылку на локальный/тестовый прототип, список реализованного, список проверенного, скриншоты ПК/телефона и нерешённые проблемы. Не переходи к следующему этапу, пока я явно не напишу «Этап N принят, переходи к N+1».

### Формат работы на каждом этапе

1. Заказчик: «Выполни этап N по ТЗ. Покажи результат и проверку. Другие этапы не начинай».
2. Агент: реализует в отдельном логическом изменении/коммите, запускает проект, выполняет тесты, показывает результат, перечисляет отклонения.
3. Заказчик: проходит сценарии и присылает конкретные замечания (экран → действие → ожидаемое → фактическое).
4. Агент: исправляет замечания и повторно демонстрирует.
5. Заказчик: «Этап N принят» и только затем запускает следующий.

### Правила для агента

- Не расширять функциональность без согласования; **никаких ачивок**, самостоятельной регистрации, Telegram, платных функций и лишних кабинетов.
- Не заменять правильную проверку математических ответов безусловным доверием ИИ.
- Не хранить пароли и токены в исходном коде; не помещать файлы ошибок в общедоступную директорию.
- Не рисовать фальшивый прогресс: все значения идут из сохранённых данных пользователя.
- Сначала закончить и проверить **один тип** и весь его цикл, затем масштабировать каталог.
- После изменений запускать автоматические тесты и вручную проверять ключевой сценарий в браузере.
- Все спорные продуктовые решения оформлять в `DECISIONS.md`, все выявленные дефекты — в `BUGS.md`; новые пункты не менять молча.

## 12. Что нужно утвердить на этапе 1

1. **Версия экзамена:** 2026 (12 номеров) или проект 2027 (13 номеров); конкретное наполнение каталога типов.
2. **Источник банка:** собственный проверенный набор, импорт разрешённых материалов, порядок проверки ответов и изображений.
3. **Момент зачёта при ошибке:** обучающий этап завершается только после правильного ответа; контрольная ошибка/помощь требует новой попытки — именно так заложено в ТЗ.
4. **Политика устаревшего повторения:** пропущенные интервалы не пропускать автоматически; выполнять актуальные проверки последовательно.
5. **Окно цитирования:** выделение старого текста из видимой переписки; в модель передаётся только выделенный фрагмент сверх последних 10 сообщений.
6. **Границы диагностики:** ошибки в свободном чате не записываются, даже если ИИ увидел неверный результат; фиксируются только ошибки задач платформы после объяснения учеником.

После утверждения этих пунктов ТЗ следует считать базовой спецификацией. Любое изменение правил фиксировать отдельной версией документа.
