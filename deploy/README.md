# Развёртывание «Пятёрки»

Рабочий сайт: https://ege-matan.virgo-vpn.site/

## Файлы на сервере

- `/srv/pyaterka/current` — ссылка на текущий выпуск, пользователь приложения не может менять код.
- `/srv/pyaterka/releases/` — выпуски кода.
- `/srv/pyaterka/venv` — Python-окружение.
- `/srv/pyaterka/state` — приватная SQLite, ключ Aijuju, фотографии, ошибки и VAPID; владелец pyaterka, каталоги 0700, файлы 0600.
- `/srv/pyaterka/static` — только собранные публичные ресурсы.
- `/etc/pyaterka.env` — параметры production и отдельный секрет Django, root:root 0600.
- `/var/backups/pyaterka` — семь последних ежедневных приватных резервных копий.

SSH-данные читаются локальным `remote.py` из корневой `.env`. Пароль не попадает в argv и логи. Ключ хоста сохранён в приватной `.runtime/deploy_known_hosts`. Исходную `.env` на сервер не копируем.

## Проверка служб

```bash
systemctl status pyaterka nginx
systemctl list-timers pyaterka-notifications.timer pyaterka-backup.timer certbot.timer
journalctl -u pyaterka -n 50 --no-pager
```

Gunicorn слушает только 127.0.0.1:8091. nginx обслуживает HTTPS и /static/, остальные запросы передаёт Django. Запуск — config.production_settings; HTTPS-заголовки задаёт nginx. Приложение не запускается root-пользователем.

Уведомления проверяются раз в минуту systemd timer. Резервная копия — ежедневно в 03:20 по часовому поясу сервера (при развёртывании UTC). Включено автоматическое продление сертификата и reload nginx после него. Для телефона открыть HTTPS-сайт, добавить его на главный экран, войти и нажать «Настроить уведомления». Разрешение на устройстве выдаёт сам ученик.

## Резервная копия и восстановление

Разовая копия: `systemctl start pyaterka-backup.service`. Проверка снимка: `python3 /srv/pyaterka/current/deploy/verify_backup.py`. SQLite копируется через backup API; работающий файл БД не архивируется напрямую. В архиве есть база, приватные файлы и pyaterka.env; архивы только root:root 0600.

Перед восстановлением остановить `pyaterka.service` и `pyaterka-notifications.timer`, отдельно сохранить текущее state. Распаковать выбранный архив в закрытый временный каталог; восстановить state и `/etc/pyaterka.env`, вернуть владельца pyaterka и права 0700/0600. Только после проверки целостности запустить службы. Проверка восстановления в текущем деплое выполнена на временном снимке, рабочая база не перезаписывалась.

Для следующих обновлений переносить только код в новый release и менять current. Никогда не загружать локальную SQLite поверх рабочей базы: после запуска сайта источником актуальных данных является сервер. Подготовительные скрипты в этой папке документируют первый деплой; finish-server.sh специально отказывается перезаписывать существующую базу.

Копии пока находятся на том же сервере. Для защиты от потери самого VPS потребуется отдельно настроить внешнее хранение резервных копий.
